# Xpay Transaction Processing System

## 📌 Overview

Xpay is a backend transaction processing system designed to handle **account-to-account transfers**, **commission computation**, and **daily transaction summaries** in a reliable, auditable, and scalable way.

The system follows real-world financial system patterns:

* Transactions are processed immediately
* Commissions are calculated asynchronously via scheduled jobs
* Daily summaries are generated and persisted for reporting
* All scheduled jobs are safe for multi-instance deployments

---

## 🧱 Core Domain Concepts

### 1. Account

Represents a customer account.

***Test accounts are automatically generated by the system.***

***Available accounts:***

```java
Created account 5300000001 with balance 100000.00
Created account 5300000002 with balance 50000.00
Created account 5300000003 with balance 25000.00
```
**Key fields**:

* `accountNumber`
* `balance`

Accounts are debited and credited during transfers.

---

### 2. Transaction

Represents a single transfer attempt (successful or failed).

**Key fields**:

* `reference` – unique transaction reference
* `sourceAccount`
* `destinationAccount`
* `amount`
* `transactionFee` – 0.5% of amount (capped at 100)
* `billedAmount` – amount + fee
* `commission` – 20% of fee
* `commissionWorthy` – whether commission applies
* `commissionProcessed` – prevents double processing
* `status` – SUCCESSFUL, FAILED, INSUFFICIENT_FUND
* `createdAt`

All transaction states are persisted for audit purposes.

---

### 3. TransactionDailySummary

Stores aggregated transaction data per day.

**Key fields**:

* `summaryDate`
* `totalTransactions`
* `totalAmount`
* `totalFees`
* `totalCommission`

This table ensures historical reports remain immutable even if raw data changes.

---

## 🔄 Transfer Flow

### Transfer Process (`transfer` method)

1. Validate source and destination accounts
2. Check for sufficient balance
3. Calculate transaction fee
4. Update account balances atomically
5. Persist transaction record

⚠️ **Important design decision**:

* Commission is **NOT calculated during transfer**
* This avoids blocking user transactions

---

## 💰 Commission Logic

### Rules

* Transaction fee = **0.5% of amount (max 100)**
* Commission = **20% of transaction fee**

### Commission Processing Strategy

* Only **SUCCESSFUL** transactions are eligible
* Commission is processed by a scheduled job
* Each transaction is processed exactly once

### Why async commission processing?

* Improves transaction response time
* Prevents complex rollback scenarios
* Aligns with real-world payment systems

## ⏱️ Scheduled Jobs

### 1. Daily Commission Processor

```java
@Scheduled(cron = "0 0 0/12 * * ?", zone = "Africa/Lagos")
```

**Runs:**

* 12:00 AM
* 12:00 PM

**Responsibilities:**

* Fetch unprocessed successful transactions
* Calculate commission
* Mark transactions as processed

Uses **ShedLock** to prevent duplicate execution in clustered environments.

---

### 2. Daily Transaction Summary Generator

```java
@Scheduled(cron = "0 0 1 * * ?", zone = "Africa/Lagos")
```

**Runs:**

* Daily at 01:00 AM

**Responsibilities:**

* Generate previous day’s transaction summary
* Persist summary for reporting

Summaries are immutable once generated.

---

GenerationMode.GENERATE_ONLY

## Get Transactions (Filtered & Paginated)

**Endpoint**

```
GET /api/transactions
```

**Description**
Returns a paginated list of transactions with optional filtering by status, account number, and date range. This endpoint is optimized for reporting, dashboards, and audit use‑cases.

---

### Supported Query Parameters

| Parameter     | Type      | Required | Description                                                                              |
|---------------| --------- | -------- | ---------------------------------------------------------------------------------------- |
| `status`      | String    | No       | Transaction status (e.g. `SUCCESSFUL`, `FAILED`, `INSUFFICIENT_FUND`). Case‑insensitive. |
| `accountNumber` | String    | No       | Filters transactions where the account is either source or destination.                  |
| `startDate`   | LocalDate | No       | Start date for transaction creation (inclusive).                                         |
| `endDate`     | LocalDate | No       | End date for transaction creation (inclusive).                                           |
| `page`        | Integer   | No       | Page number (0‑based). Default = 0                                                       |
| `size`        | Integer   | No       | Page size. Default = 20                                                                  |
| `sort`        | String    | No       | Sorting field (e.g. `createdAt,desc`).                                                   |

---

### Business Rules

* If **both `startDate` and `endDate` are provided**, the system validates that `startDate ≤ endDate`.
* If **no filters are supplied**, all transactions are returned (paginated).
* If `status` is invalid, the request fails with a validation error.
* Date filtering is performed using the transaction `createdAt` timestamp.

---


### Example Requests

```
GET /api/transactions?status=SUCCESSFUL&accountNumber=53000001&startDate=2025-01-01&endDate=2025-01-31&page=0&size=10
```

```
GET /api/transactions?page=0&size=20
```

---

### Design Notes

* Uses database‑level pagination for performance.
* Prevents large result sets from overwhelming memory.
* Specification pattern keeps query logic extensible and maintainable.
